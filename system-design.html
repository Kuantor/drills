Reference — the patterns behind all sixty answers
  1. The trap is usually the more sophisticated option. Redlock over fencing tokens, a sliding-window log over a token bucket, active–active over a read replica, microservices over a modular monolith. Ask what the sophistication buys here.
  2. Constraints select the answer. A deadline, an audit, a team's existing tools. An answer that ignores the stated constraint is wrong, however good the architecture.
  3. Fix the cause, not the symptom. Caching an N+1, adding capacity to a hot key, shorter timeouts plus more retries, a bigger pool for slow queries: the graph improves and the defect stays.
  4. Name the failure precisely. Simultaneous execution wants a lock; repeated execution wants idempotency; concurrent divergence wants a merge strategy.
  5. Bursts and sustained imbalance are different. Buffers, autoscaling and jitter absorb bursts. Only reducing input or shedding to durable storage fixes an imbalance.
  6. Scope the expensive guarantee. Read-your-writes for the user who just wrote, primary reads for payment status, strong consistency where money is.
  7. Ask whether the problem is volume or shape. Replicas fix volume. Projections, different engines and different indexes fix shape.
  8. Two systems can't be updated atomically. "Keep the cache and the database both current" really means "lose one occasionally". Invalidate, or make the invalidation durable.
  9. Known shape versus discovered shape decides coordination: a DAG when dependencies are known, a central controller when they aren't.
